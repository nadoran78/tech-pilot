# 뉴스 설명·분류 결과 저장 및 재실행 제안

- **Status:** Accepted
- **Applies to:** Phase 4, Issue #65
- **Purpose:** 원본 연결·입력 추적·결과 보존·재처리·실패의 최소 논리 경계를 제안한다.
- **Read when:** 생성 결과 저장·재실행·실패 처리 또는 후속 migration을 설계할 때
- **Related documents:** [ADR 0007](../decisions/0007-news-understanding-execution-storage.md), [입력·출력 계약](news-understanding-input-output.md), [평가 기준](news-understanding-evaluation.md), [뉴스 원본 계약](news-item.md), [기존 SQLite 결정](../decisions/0003-sqlite-news-item-storage.md)

## 상태와 범위

2026-10-18 사용자가 ADR 0007의 실행·저장·재실행안과 입력·평가안을 명시적으로 승인했다. Issue #67에서 기존 SQLite에 원본·수집 기록과 분리한 종료 시도 테이블을 구현한다. 기존 원본·수집 계약은 바꾸지 않으며 실제 운영 DB migration은 실행하지 않는다.

## 최소 논리 기록

| 구분 | 제안할 정보·제약 |
|---|---|
| 식별·원본 연결 | 고유 시도 ID, 원본 저장 항목 ID·source_id·evidence_url. 제목이나 URL만으로 결과를 다른 항목에 연결하지 않음 |
| 입력 추적 | 처리에 사용한 최소 메타데이터 스냅샷·fingerprint·입력 계약 버전·입력 수준·요청 종류(제목 설명 또는 원문 요약 요청) |
| 처리 추적 | 방법 식별자·처리 버전·설정/규칙 버전. 향후 모델 도입 시 추가할 provenance는 별도 결정; 이번에는 모델 값 없음 |
| 시각 | 시작·종료의 timezone 포함 UTC 시각. 뉴스 발표 시각과 구분 |
| 실행 상태 | completed(검증된 결과 확정) 또는 failed(처리/검증 오류). 품질 평가의 합격을 뜻하지 않음 |
| 내용 결과 | 입력·출력 계약의 described/insufficient_information/deferred 등 내용 상태, 허용 시 생성 텍스트·잠정 분류·근거 필드·한계·보류 사유 |
| 오류 | failed에서는 안전한 분류 코드와 결과 없음. 원시 예외·DB 경로·비밀 값·본문·프롬프트 전체를 로그처럼 복사하지 않음 |

내용 상태와 실행 상태는 별개다. 예컨대 충분하지 않은 입력을 정상적으로 판별한 completed + insufficient_information은 실패가 아니며, 처리 예외를 정보 부족으로 숨기면 안 된다. 메타데이터 경로의 summarized 출력이나 입력 밖 근거 문자열은 결과 검증 오류로 failed 처리하고 정상 결과로 노출하지 않는다. deferred는 이유가 있는 보류 결과이며 참조 없는 사전 거부와 다르다. 오류 코드·직렬화·제약은 아래 첫 구현 연결을 따른다.

원본 참조가 없거나 승인되지 않은 경로는 실행 전에 거부·보류하고 생성 결과를 잘못된 원본에 연결하지 않는다. 이 사전 거부는 원본에 연결된 completed/failed 시도 기록 대상과 구분한다. 참조 없는 거부 진단의 영속화는 첫 저장 구현에 포함하지 않는 방향이다.

## 보존·재실행 제안

1. 승인된 최소 입력만 로컬 스냅샷으로 보관해 원본이 나중에 수정돼도 어떤 제목을 처리했는지 확인한다. 본문·추가 발췌·비밀 값은 포함하지 않는다. 스냅샷은 공개 Git에 넣지 않는다.
2. 재사용 키는 **원본 ID + 사용 입력 fingerprint + 요청 종류 + 입력/출력 계약 버전 + 방법/처리/설정 버전**으로 제안한다. 사용 필드와 정규화·fingerprint 계산은 구현 이슈에서 결정한다. 제목만 비교하거나 해시만으로 다른 원본을 합치지 않는다.
3. 같은 키의 확정된 정상 결과가 있으면 기본 재실행은 이를 재사용하고 새 처리·중복 결과를 만들지 않는다. 정상적으로 판별한 정보 부족도 포함한다. 동일 키 실패만 있다면 자동 재시도하지 않고 사용자가 다시 실행할 때 새 시도를 추가할 수 있다.
4. 입력·요청·계약·처리 버전이 바뀌면 새 키로 새 기록을 추가하고 기존 결과를 덮어쓰지 않는다. 같은 키 강제 재처리는 첫 구현에서 제공하지 않는 방향이다. 필요 시 별도 시도 선택·비교 계약을 검토한다.
5. latest 하나만 모든 요청에 쓰지 않는다. 조회는 현재 입력/방법/요청의 정확한 키에 맞는 결과를 선택한다. 키가 달라 과거 결과만 있으면 과거임을 표시하고 현재 결과인 것처럼 노출하지 않는다.
6. 원본 뉴스·HTTP validator·Google 예약·collection_runs는 이 처리로 변경하지 않는다. 자동 삭제·원본 연쇄 삭제·정리 명령은 포함하지 않는다.

## 처리·저장 실패 경계

첫 구현은 단일 수동 실행을 전제로 한다는 가정이다. 동시 실행 중복 방지·잠금·이력 복구는 추후 요구가 생기면 별도 계약이 필요하며 지금 보장하지 않는다.

- 처리·결과 검증 뒤 결과와 시도 상태를 짧은 트랜잭션으로 함께 확정하는 방향을 제안한다. 네트워크·모델 처리 중 열린 쓰기 트랜잭션을 유지하는 설계는 채택하지 않는다.
- 처리 오류는 저장소가 정상일 때 안전한 실패 기록을 남긴다. failed 시도는 재사용 가능한 정상 결과를 대체하지 않는다.
- 저장 자체가 실패하면 안전한 오류로 종료하고 저장됐다고 보고하지 않는다. 자동 재처리·자동 재저장을 하지 않으며 원본도 되돌리지 않는다. 일부 항목 저장 후 실패한 배치는 성공 항목이 남을 수 있음을 알린다. 재실행은 키별로 판단한다.
- 첫 제안은 종료 후 기록이므로 강제 종료 시 시도 기록이 없을 수 있다. 기록 부재로 미실행·성공·실패를 추정하지 않는다. 수집용 ADR 0006의 running 복구 경계를 생성 처리에 자동 적용하지 않으며 필요하면 별도 보완한다.

## 수작업 경계 사례

아래는 설계 점검이며 실행한 테스트·실제 DB 결과가 아니다.

| 사례 | 기대하는 동작 제안 |
|---|---|
| 같은 원본·제목·버전·제목 설명 요청 재실행 | 기존 completed 결과 재사용, 새 처리 없음 |
| 제목이 수정되거나 규칙 버전이 변경됨 | 새 키·새 결과; 이전 결과와 당시 입력 스냅샷 보존 |
| 동일 메타데이터에 원문 요약 요청 | 별도 요청 키로 insufficient_information; 제목 설명을 원문 요약으로 재사용하지 않음 |
| 모호한 제목 | completed + insufficient_information·판단 불가, 사유와 원본 연결 유지 |
| 없는 원본 참조 | 사전 거부·보류, 잘못된 원본 연결·내용 생성 없음 |
| 처리 예외 또는 금지된 summarized 출력 | 안전한 failed, 정상 결과 없음; 자동 재시도 없음 |
| 저장 오류 또는 프로세스 강제 종료 | 완료 저장 주장 금지; 기록 누락 가능성과 운영 한계 표시 |

Issue #67의 임시 DB·가짜 처리기 테스트로 같은 키 재사용·변경 키 보존·요청 분리·실패/보류·저장 오류·기존 수집 상태 불변을 검증한다. 이후 승인된 평가 기준으로 읽기 유용성과 분류를 따로 평가한다.

## 첫 구현 연결 (Issue #67)

- [입력·요청·결과 모델](../../src/tech_pilot/understanding/models.py): `title-v1` 입력/출력 계약만 지원한다. 스냅샷은 원본 ID, source_id, evidence_url, title, published_at(누락은 null)로 제한한다. excerpt·raw_metadata·본문·수집 시각은 처리 입력이 아니다.
- 스냅샷은 필드를 바꾸지 않고 UTF-8 JSON(`ensure_ascii=False`, 키 정렬, 공백 없는 구분자)으로 직렬화해 SHA-256 fingerprint를 계산한다. 원본 ID·fingerprint·요청 전체를 같은 방식으로 해시한 값이 재사용 키다. 요청에는 종류·입출력 버전·방법·처리·설정 버전을 모두 포함한다. 지원하지 않는 계약 버전은 거부한다.
- [migration 5](../../src/tech_pilot/storage/migrations.py)의 `understanding_attempts`에 스냅샷/요청/결과 JSON, UTC 시작·종료 시각, 실행 상태·안전한 오류 코드를 저장한다. [ADR 0008](../decisions/0008-logical-reference-integrity.md)에 따라 처음부터 물리적 외래키 없이 논리적 news_id 참조를 사용한다. completed 키의 부분 unique index와 NOT NULL·CHECK 제약은 유지한다. 동시 실행 품질·재시도는 보장하지 않는다.
- [저장소](../../src/tech_pilot/storage/understanding.py)는 짧은 트랜잭션에서 원본 존재·스냅샷 일치를 재확인하고 종료 기록을 추가한다. 외부 처리 중 쓰기 잠금을 잡지 않는다. 기존 이력을 갱신·삭제하는 API는 제공하지 않는다.
- [처리 서비스](../../src/tech_pilot/understanding/service.py) `process_news`는 주입한 처리기를 최대 1회 호출한다. 참조 오류는 `InputRejected`, 저장 실패는 `UnderstandingStorageError`로 구분한다. 처리 예외는 `processing_failed`, 결과 구조 오류는 `validation_failed`로 기록하며 원시 예외는 보관하지 않는다. 강제 종료는 기록이 없을 수 있다.
- 원문 요약 요청에 설명 결과를 반환하거나 title에 없는 근거 문자열을 사용하면 검증 실패다. 설명 텍스트의 의미·분류의 정확성은 구조 검사만으로 보장하지 않으며 사람 평가 대상이다. 실제 규칙·CLI·표본 평가는 포함하지 않는다.
- 검증 진입점: [계약·실행·저장 테스트](../../tests/test_understanding.py), [기존 migration 회귀 테스트](../../tests/test_news_repository.py).

## 규칙 처리기 연동 (Issue #69)

[제목 규칙 기준선](news-understanding-rules.md)의 `rule_request`와 `apply_title_rules`를 `process_title_with_rules`로 연결한다. 기존 `process_news`의 원본 검증·저장·키 재사용·안전한 오류 경계를 그대로 사용하며 새 migration이나 저장 필드를 추가하지 않는다. 규칙이 정상적으로 판단 불가를 반환하면 completed 결과로 재사용한다. 규칙 버전이 바뀌면 새 키로 저장하고 기존 결과를 보존한다. 검증은 [규칙·저장 연동 테스트](../../tests/test_title_rules.py)를 따르며 CLI·운영 DB·실제 뉴스 평가는 포함하지 않는다.

## 읽기 전용 이력 조회 (Issue #71)

`SQLiteUnderstandingRepository.read_history(news_id, limit=10)`은 SQLite URI `mode=ro`로 연결해 원본 스냅샷과 ID 내림차순 이력을 같은 읽기 트랜잭션에서 반환한다. LIMIT은 SQL에 적용하고 조회 연결을 닫는다. 없는 DB는 만들지 않으며 기존 결과 테이블이 없으면 이력을 비워 반환한다. 조회 경로는 기존 쓰기 API와 달리 migration을 적용하지 않는다. CLI 출력·종료 코드·현재/과거 구분 기준은 [수동 운영 문서](../runbooks/news-understanding.md)를 따른다. 새 schema·migration은 없다.
