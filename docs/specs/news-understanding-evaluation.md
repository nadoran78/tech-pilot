## 평가 범위와 표본 구성안

2026-10-18 사용자가 아래 표본 구성안·평가 절차·기준을 명시적으로 승인했다(Issue #67). 아직 모델을 실행하거나 실제 품질 평가를 수행하지 않았다. 승인된 것은 평가 방법이지 개별 정답이나 평가 통과가 아니다. Issue #67의 임시 DB·가짜 처리기 테스트는 저장 계약 검증이며 이 품질 평가를 대체하지 않는다.

후속 평가 표본은 **12개**를 시작점으로 제안한다. 기술·제품 동향·활용/해설·비기술 소식·판단 불가를 각 3개씩 의도적으로 구성하고, 양 출처·시각 누락·모호한 제목·플랫폼과 게시자 공식성 차이를 교차 포함한다. 2026-10-21 사용자 승인으로 [현재 범주 정의](news-understanding-input-output.md#분류-범주)를 따르며, 취소·연기·부정·예정과 취소 후 재공개 문맥도 평가 사례로 포함한다. 실제 분포나 통계적 성능을 추정하는 표본이 아니다. 범주를 채우기 어려우면 합성 사례와 실제 사례를 구분해 보고하고 임의로 정답을 강제하지 않는다.

실제 표본은 별도 승인된 평가 작업에서 선택하고 입력 스냅샷·선정 이유·기대 상태·허용 범주·근거 필드·검토자를 기록하는 방향을 제안한다. 입력은 개인 로컬에 유지하며 제목·원문·출력 전체를 공개 PR에 복사하지 않는다. 공개 fixture에는 합성 자료만 사용한다. 이번 문서는 실제 표본 12개를 선정했다는 기록이 아니다.

## 예시 기반 설계 점검

아래는 **작성한 합성 제목과 수작업 기대 출력**이며 모델 결과나 실제 기사 제목이 아니다. 모두 제목·출처 표식·원본 연결만 있고 본문은 없다고 가정한다. URL은 합성 식별자로만 취급한다.

| 합성 입력 | 허용 가능한 출력 예시 | 금지/보류할 내용 |
|---|---|---|
| 「테스트 라이브러리 A 1.0 공개」 | described: 제목 인용 / 기술·제품 동향(잠정), 근거 title, 원문 미열람 | 성능·라이선스·출시 지역 추가, summarized 표시 |
| 「테스트 모델 출시 연기」 / 「Example model canceled release finally open!」 | described: 제목 인용 / 기술·제품 동향(잠정) | 취소·연기 단어만으로 제외, 현재 출시 상태나 실제 재출시를 확정 |
| 「How to run a model」 / 「Example model released?」 | 각각 활용·해설 / 기술·제품 동향(잠정), 제목 인용 | 지시문 표현·물음표만으로 제외, 질문을 검증된 발표 사실로 재서술 |
| 「Model released https://example.com/tutorial」 | 기술·제품 동향, 근거 Model·released, URL은 표시 제목에 보존 | URL 안 tutorial을 활용·해설 근거로 사용 |
| 「https://example.com/model/release」 | 정보 부족·판단 불가 | URL의 경로·호스트·쿼리만으로 기술 관련성을 분류 |
| 「테스트 도구 B 사용법」 | described: “제목은 테스트 도구 B 사용법을 다룬다.” / 활용·해설(잠정) | 실제 사용 절차·프로젝트 적용 효과 생성 |
| 「테스트 조직의 연례 문화 행사」 | described / 비기술 소식(잠정), 제목에 행사 명시 | 도메인이 AI 관련이라는 이유로 모델 출시로 분류 |
| 「다음 장을 시작하며」 | insufficient_information, 생성 텍스트 비움 / 판단 불가, 이유: 주제·내용 부족 | 사전 지식으로 특정 제품·발표 내용 추정 |

위 입력에 원문 요약을 요청하면 모두 insufficient_information이 기대값이다. 제목에서 분류할 수 있어도 내용 요약에 충분한 것은 아니다. 같은 명확한 제목에서 발표 시각만 빠진 경우 분류는 유지할 수 있지만 최신성은 주장하지 않는다. 원본 연결 자체가 손상된 변형은 deferred로 구분한다.

[기존 Google fixture](../../tests/fixtures/google_ai_blog_feed.xml)의 “Synthetic release”는 기술 대상이 명시되지 않았으므로 제목만으로 기술·제품 동향을 강제하지 않는 판단 불가 사례다. description의 “Must not be stored”는 입력으로 사용하지 않는다. 이 확인은 수작업 설계 점검이며 모델 정확도 측정이 아니다.

## 항목별 검토표 제안

| 항목 | 판정·기록 방식 |
|---|---|
| 입력·원본 추적 | 사용 입력 수준·필드·원본 참조가 일치하는지 통과/수정필요 |
| 근거 충실성 | 문장별로 입력에 있는 사실인지 확인. 새 수치·출시 범위·효과가 생기면 중대 오류 |
| 처리 수준 | 제목 설명을 원문 요약으로 표시했는지 확인. 잘못된 summarized는 중대 오류 |
| 정보 부족·보류 | 내용 부족·손상 입력에서 기대 상태와 이유가 있는지 통과/수정필요 |
| 분류 | 기대 허용 범주와 일치/불일치/검토자 불일치. 공식성·효용을 분류에서 추정하지 않음 |
| 발견·선별 | 기술 관련 소식의 누락, 무관한 소식 포함, 불필요한 판단 보류를 건수·사유로 별도 기록. 출시 여부 판정은 평가 목표가 아님 |
| 읽기 유용성 | 사용자에게 제목 목록 대비 도움 있음/없음/판단 유보 및 이유 |

먼저 검토자가 **허용된 입력만 보고** 기대 상태·범주와 근거를 작성하고 이후 결과를 대조하는 절차를 제안한다. 애매한 입력은 판단 불가를 정답 후보로 두고, 불일치는 근거와 함께 사용자에게 확인한다. 추후 실제 내용 기반 평가를 하려면 그 내용 입력이 먼저 승인·확보되어야 한다.

## 통과 기준 제안과 보고

- 첫 소량 평가에서는 중대 오류(근거 없는 사실·제목 설명의 원문 요약 오표시) 0건, 원본 추적·정보 부족/보류 처리 전 항목 충족을 안전 기준 후보로 둔다.
- 분류는 12개 중 10개 이상 허용 범주 일치를 승인된 검토 출발점으로 둔다. 검토자 불일치와 미평가도 분모에서 숨기지 말고 건수·사유를 별도 보고한다. 제외 후 높은 점수만 보고하지 않는다.
- 위 수치 달성만으로 제품 품질을 확정하지 않는다. 사용자 읽기 유용성 검토와 오류 사례 확인 뒤 반복 여부·표본 확대·기준 수정을 결정한다. 자동 합격이나 통계적 일반화를 하지 않는다.
- 취소·부정 표현이 있다는 이유만으로 오류나 정보 부족으로 판정하지 않는다. 추가 필터는 실제 평가에서 확인한 문제와 과도한 보류 등 부작용을 함께 검토한 뒤 도입한다. 현재 실제 표본 평가는 미실행이다.

보고에는 입력 경로·표본 구성·기대값 작성 근거·오류와 보류·분류 불일치·사용자 의견·미검증 범위를 포함한다. 최초 Issue #63은 계약·예시·평가 제안 작성이었다. 승인 뒤 Issue #67에서 저장 기반을 구현하고, 구체적 규칙·수동 진입점·실제 표본 평가는 후속 이슈로 분리한다. 현재 12개 평가 통과나 읽기 유용성 확보를 주장하지 않는다.
