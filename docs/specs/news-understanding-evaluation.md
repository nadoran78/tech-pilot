## 평가 범위와 표본 구성안

아직 모델을 실행하거나 실제 품질 평가를 수행하지 않았다. 아래 수량·정답·통과 기준은 사용자 합의 전 제안이다. 이번에는 운영 DB·원문에 접근하지 않고 기존 fixture와 합성 예시로 계약의 모호함만 점검한다.

후속 평가 표본은 **12개**를 시작점으로 제안한다. 기술 발표·활용/해설·비기술 소식·판단 불가를 각 3개씩 의도적으로 구성하고, 양 출처·시각 누락·모호한 제목·플랫폼과 게시자 공식성 차이를 교차 포함한다. 실제 분포나 통계적 성능을 추정하는 표본이 아니다. 범주를 채우기 어려우면 합성 사례와 실제 사례를 구분해 보고하고 임의로 정답을 강제하지 않는다.

실제 표본은 별도 승인된 평가 작업에서 선택하고 입력 스냅샷·선정 이유·기대 상태·허용 범주·근거 필드·검토자를 기록하는 방향을 제안한다. 입력은 개인 로컬에 유지하며 제목·원문·출력 전체를 공개 PR에 복사하지 않는다. 공개 fixture에는 합성 자료만 사용한다. 이번 문서는 실제 표본 12개를 선정했다는 기록이 아니다.

## 예시 기반 설계 점검

아래는 **작성한 합성 제목과 수작업 기대 출력**이며 모델 결과나 실제 기사 제목이 아니다. 모두 제목·출처 표식·원본 연결만 있고 본문은 없다고 가정한다. URL은 합성 식별자로만 취급한다.

| 합성 입력 | 허용 가능한 출력 예시 | 금지/보류할 내용 |
|---|---|---|
| 「테스트 라이브러리 A 1.0 공개」 | described: “제목은 테스트 라이브러리 A 1.0 공개를 알린다.” / 기술 발표(잠정), 근거 title, 원문 미열람 | 성능·라이선스·출시 지역 추가, summarized 표시 |
| 「테스트 도구 B 사용법」 | described: “제목은 테스트 도구 B 사용법을 다룬다.” / 활용·해설(잠정) | 실제 사용 절차·프로젝트 적용 효과 생성 |
| 「테스트 조직의 연례 문화 행사」 | described / 비기술 소식(잠정), 제목에 행사 명시 | 도메인이 AI 관련이라는 이유로 모델 출시로 분류 |
| 「다음 장을 시작하며」 | insufficient_information, 생성 텍스트 비움 / 판단 불가, 이유: 주제·내용 부족 | 사전 지식으로 특정 제품·발표 내용 추정 |

위 네 입력에 원문 요약을 요청하면 모두 insufficient_information이 기대값이다. 분류 가능한 앞 세 항목도 내용 요약에 충분한 것은 아니다. 같은 명확한 제목에서 발표 시각만 빠진 경우 분류는 유지할 수 있지만 최신성은 주장하지 않는다. 원본 연결 자체가 손상된 변형은 deferred로 구분한다.

[기존 Google fixture](../../tests/fixtures/google_ai_blog_feed.xml)의 “Synthetic release”는 무엇을 공개했는지 알 수 없으므로 제목만으로 기술 발표를 강제하지 않는 판단 불가 사례다. description의 “Must not be stored”는 입력으로 사용하지 않는다. 이 확인은 수작업 설계 점검이며 새 자동 테스트나 모델 정확도 측정이 아니다.

## 항목별 검토표 제안

| 항목 | 판정·기록 방식 |
|---|---|
| 입력·원본 추적 | 사용 입력 수준·필드·원본 참조가 일치하는지 통과/수정필요 |
| 근거 충실성 | 문장별로 입력에 있는 사실인지 확인. 새 수치·출시 범위·효과가 생기면 중대 오류 |
| 처리 수준 | 제목 설명을 원문 요약으로 표시했는지 확인. 잘못된 summarized는 중대 오류 |
| 정보 부족·보류 | 내용 부족·손상 입력에서 기대 상태와 이유가 있는지 통과/수정필요 |
| 분류 | 기대 허용 범주와 일치/불일치/검토자 불일치. 공식성·효용을 분류에서 추정하지 않음 |
| 읽기 유용성 | 사용자에게 제목 목록 대비 도움 있음/없음/판단 유보 및 이유 |

먼저 검토자가 **허용된 입력만 보고** 기대 상태·범주와 근거를 작성하고 이후 결과를 대조하는 절차를 제안한다. 애매한 입력은 판단 불가를 정답 후보로 두고, 불일치는 근거와 함께 사용자에게 확인한다. 추후 실제 내용 기반 평가를 하려면 그 내용 입력이 먼저 승인·확보되어야 한다.

## 통과 기준 제안과 보고

- 첫 소량 평가에서는 중대 오류(근거 없는 사실·제목 설명의 원문 요약 오표시) 0건, 원본 추적·정보 부족/보류 처리 전 항목 충족을 안전 기준 후보로 둔다.
- 분류는 예를 들어 12개 중 10개 이상 허용 범주 일치를 검토 출발점으로 제안한다. 검토자 불일치와 미평가도 분모에서 숨기지 말고 건수·사유를 별도 보고한다. 제외 후 높은 점수만 보고하지 않는다.
- 위 수치 달성만으로 제품 품질을 확정하지 않는다. 사용자 읽기 유용성 검토와 오류 사례 확인 뒤 반복 여부·표본 확대·기준 수정을 결정한다. 자동 합격이나 통계적 일반화를 하지 않는다.

보고에는 입력 경로·표본 구성·기대값 작성 근거·오류와 보류·분류 불일치·사용자 의견·미검증 범위를 포함한다. 이번 이슈의 완료는 **계약·예시·평가 제안 작성**이며 12개 평가 통과나 구현 완료가 아니다. 승인 후 입력 계약 확정 → 기술·저장 결정 → 최소 구현·실제 표본 평가 순서로 이슈를 분리한다.
