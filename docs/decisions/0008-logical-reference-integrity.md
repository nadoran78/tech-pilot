# 0008: 물리적 외래키 기본 미사용과 논리적 참조 검증

- **Status:** Accepted
- **Date:** 2026-10-18
- **Applies to:** 모든 저장 테이블과 후속 migration
- **Purpose:** 테이블 간 참조를 DB 외래키 대신 어떻게 관리할지 정한다.
- **Read when:** 테이블 관계·저장·삭제·데이터 이관을 설계하거나 수정할 때
- **Related documents:** [ADR 0007](0007-news-understanding-execution-storage.md), [저장·재실행 계약](../specs/news-understanding-storage.md), [기술 스택](../architecture/tech-stack.md)

## Context

Issue #67 / PR #68 검토 중 사용자가 물리적 외래키를 기본적으로 사용하지 않는 기조의 문서화와 이번 테이블의 외래키 제거를 명시적으로 요청했다. 현재는 소량·단일 로컬 SQLite 운영이며, 스키마 변경·데이터 이관의 유연성을 우선한다. 성능 개선을 측정하거나 외래키가 무익하다고 판단한 결정은 아니다.

## Decision

- 신규·변경 테이블에는 물리적 `FOREIGN KEY`/`REFERENCES`를 기본적으로 추가하지 않는다. 참조 오류의 피해가 크거나 복구가 어려운 관계는 별도 ADR와 사용자 승인으로 예외를 검토한다.
- 논리적 참조 필드와 관계 문서는 유지한다. 저장 경계에서 참조 대상의 존재·필요한 입력 일치를 확인하고, 필요한 검증과 쓰기를 같은 트랜잭션으로 묶는다.
- `NOT NULL`, `UNIQUE`, `CHECK`와 필요한 인덱스는 별개이며 유지한다. 외래키 미사용을 모든 무결성 제약 제거로 확대하지 않는다.
- 원본 삭제·참조 ID 변경·이관 기능을 추가하기 전에 관련 이력의 보존·삭제·재연결 정책과 검증·복구 방법을 결정한다. 고아 기록 자동 삭제나 주기적 정화 작업은 이번 결정으로 도입하지 않는다.

## 이번 적용과 이관

`understanding_attempts.news_id`는 논리적 참조로 유지한다. `save_attempt`의 짧은 쓰기 트랜잭션에서 원본 존재·스냅샷 일치를 확인하는 코드는 유지한다. DB에 직접 쓰는 도구·스크립트까지 이 검증이 강제되지는 않으므로 해당 경로는 별도 검증 책임을 가진다.

후속 사용자 요청에 따라 병합 전 migration 5의 외래키 선언을 직접 제거하고 불필요한 migration 6은 삭제한다. 새 DB와 기존 기준 버전 4에서 적용한 DB 모두 버전 5에서 외래키 없는 테이블을 생성한다. NOT NULL·CHECK·정상 결과 unique index와 원본 참조 검증은 유지한다. 이전의 5→6 전환안은 채택하지 않는다. 실제 운영 DB에는 실행하지 않는다.

migration 수정·새 버전 추가의 판단 기준은 [개발 워크플로의 Migration Change Policy](../process/development-workflow.md#migration-change-policy)를 따른다. 이전 PR 커밋의 스키마를 보존할 로컬 DB에 적용했다면 수정된 5가 재실행되지 않으므로 별도 이관 판단이 필요하다. 이번 작업에서 로컬 DB를 삭제·재생성하거나 migration 기록을 변경하지 않는다.

## Consequences

스키마 관계의 DB 강제를 줄이는 대신 코드·테스트·운영 검증이 참조 무결성의 책임을 맡는다. 직접 SQL로 인한 원본 삭제·잘못된 참조를 DB가 막아준다고 가정하지 않는다. 현재 삭제 API는 없으며, 원본 삭제 후 이력 처리 정책은 아직 미결정이다. 금전·보안 등 높은 무결성이 필요한 관계가 생기면 예외 적용을 다시 검토한다.
